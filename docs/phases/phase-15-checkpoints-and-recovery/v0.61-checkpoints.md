# v0.61 -- Checkpoints & Log Truncation

---

## 1. Problem Statement

## Visual Model

```mermaid
flowchart LR
    A["Crash or restart"] --> B["Checkpoint"] --> C["Redo and undo"] --> D["Consistent database"]
```
Without periodic checkpoints, database recovery after a crash requires replaying the entire WAL file from the very first record, which could take hours for large databases. We need to implement a **`CheckpointManager`** that periodically flushes all dirty buffer pool pages to disk, writes checkpoint boundary markers to the WAL, and logs the set of currently active transactions — establishing a known-good recovery starting point from which only records after the checkpoint need to be replayed.

---

## 2. Step-by-Step Instructions

### Step 1: Design the Checkpoint Manager
* Create a header file `src/recovery/checkpoint_manager.h` within `namespace DB`.
* Include the buffer pool manager, WAL writer, WAL manager, and log record headers.
* Define `class CheckpointManager`:
  * Declare private member variables:
    * `bpm` (pointer to `BufferPoolManager`).
    * `wal_writer` (pointer to `WALWriter`).
    * `wal_manager` (pointer to `WALManager`).
  * Write a constructor binding all three.
  * Declare a public execution method:
    `void CreateCheckpoint(const std::unordered_map<TxID, std::shared_ptr<Transaction>>& active_txns)`

### Step 2: Implement the Checkpoint Protocol
* Implement `CreateCheckpoint(active_txns)`:
  * **Step 1 — CHECKPOINT_START**: Allocate a start LSN from the WAL manager. Create and append a `LogRecord` marked as checkpoint start.
  * **Step 2 — Flush Dirty Pages**: Call `bpm->FlushAllPages()` to write all dirty buffer pool frames to disk, clearing the dirty flag on each flushed page.
  * **Step 3 — Collect Active Transactions**: Loop through `active_txns` and gather all active `TxID` values into a vector.
  * **Step 4 — CHECKPOINT_END**: Allocate an end LSN. Create a `LogRecord` storing the collected active transaction IDs in its after-image payload (serialized via `std::memcpy`). Append this record.
  * **Step 5 — Force Flush**: Call `wal_writer->ForceFlush()` to sync both checkpoint records to disk. Update `wal_manager->SetFlushedLSN()`.

## 3. C++ Systems Features Primer

* **Checkpoints and Recovery Time**: After a crash, the recovery engine scans the WAL backward to find the most recent `CHECKPOINT_END` record. All changes already reflected in the checkpoint's dirty page flush do not need to be re-applied. Recovery replays only records from the checkpoint start onward, bounding recovery time to minutes instead of hours.
* **`std::memcpy` for Binary Payloads**: To serialize a `std::vector<TxID>` into a `std::vector<uint8_t>` payload, we compute the total byte size and use `std::memcpy` to copy the raw integer memory layout directly, avoiding complex serialization loops.
* **Buffer Pool Flush (`FlushAllPages`)**: The buffer pool manager must provide a method that iterates all its frame entries, writes dirty frames to disk via the disk manager, and resets their dirty flags.

---

## 4. Functional & Structural Requirements
* **Sequence Ordering**: Dirty page flushes must complete *before* the `CHECKPOINT_END` record is written, ensuring the checkpoint reflects a consistent state.
* **Active Transaction Registry**: The checkpoint must record which transactions were active at checkpoint time, allowing the recovery engine to determine which uncommitted changes need undo.
* **Force Flush**: Both checkpoint log records must be synced to physical disk immediately via `ForceFlush()`.
