## 1. Problem Statement

## Visual Model

    A["Key lookup"] --> B["B+ tree traversal"] --> C["Leaf entry"] --> D["Record RID"]

Once the B+ Tree node layout is defined, we must implement the point lookup routing algorithm. The searcher must start at the root node page, evaluate search keys, and navigate down child branch paths until it reaches a leaf node page. Within the leaf, it must run binary search to locate the exact key and return the corresponding document Record ID (RID).

## 2. Step-by-Step Instructions

### Step 1: Implement Page Layout Array Mapping
* Create a header file `src/index/btree_node_helpers.h` within `namespace DB`.
* Include the btree node header.
* Define helper class `BTreeNodeHelpers` containing static methods:
  * `constexpr size_t MaxLeafKeys()`:
    * Calculate capacity. Each leaf entry contains a key (`int64_t`/8 bytes) and an `RID` (6 bytes).
    * Return `BTREE_DATA_SIZE / (8 + 6)`.
  * `constexpr size_t MaxInternalKeys()`:
    * Calculate capacity. Each internal entry contains a key (`int64_t`/8 bytes) and a child `PageID` (8 bytes). We also reserve space for one extra child pointer.
    * Return `(BTREE_DATA_SIZE - sizeof(PageID)) / (8 + 8)`.
  * Define pointer getters:
    * `int64_t* InternalKeys(Page* page)`: Returns pointer to start of key array inside internal page payload.
    * `PageID* InternalChildren(Page* page)`: Returns pointer to child PageID array, residing immediately after the pre-allocated keys array space (`InternalKeys + max_size`).
    * `int64_t* LeafKeys(Page* page)`: Returns pointer to key array inside leaf page payload.
    * `RID* LeafValues(Page* page)`: Returns pointer to RID values array, residing immediately after the pre-allocated leaf keys array space (`LeafKeys + max_size`).

### Step 2: Implement Point Lookup Routing
* Create a header file `src/index/btree_search.h` within `namespace DB`.
* Include the helper and disk manager headers.
* Define `class BTreeSearcher`:
  * Add a constructor accepting a pointer to `DiskManager`.
  * Implement `RID FindKey(PageID root_id, int64_t key)`:
    * If `root_id == INVALID_PAGE_ID`, return an invalid RID immediately.
    * Set `current_id = root_id`.
    * **Routing Loop**:
      * Read `current_id` page from disk.
      * Retrieve `BTreeHeader` metadata.
      * **If Leaf**:
        * Retrieve the leaf keys array pointer.
        * Run binary search (`std::lower_bound`) on the keys array to find the first element $\ge$ `key`.
        * Calculate index offset: `index = std::distance(keys_start, iter)`.
        * Check if `index < size` and `keys[index] == key`:
          * If yes, return `values[index]`.
          * If no, return invalid RID (key not found).
      * **If Internal**:
        * Retrieve internal keys and child pointer array pointers.
        * Run binary search (`std::upper_bound`) on the keys array to find the first element $>$ `key`.
        * Calculate child index offset.
        * Set `current_id = children[child_index]` and repeat the routing loop.

## 3. C++ Systems Features Primer

* **Leaf Layout**: Storing keys and values in separate arrays:
  `[ Header ][ Key 0 | Key 1 ][ Value 0 | Value 1 ]`
  This is preferred in database design over an array of structs (`struct Entry { key; value; }`) because key arrays can be searched in CPU cache lines without loading values into memory.
* **Lower Bound vs. Upper Bound**:
  * **`std::lower_bound`**: Finds the first element that is $\ge$ value. We use it inside leaves because we are looking for the exact matching key.
  * **`std::upper_bound`**: Finds the first element that is $>$ value. We use it inside internal nodes because parent keys represent boundaries: if key is 50, keys `< 50` go to left branch (child 0), and keys `\ge 50` go to right branch (child 1).
* **`std::distance`**: A utility from `<iterator>` that calculates the index difference between two pointers/iterators.

## 4. Functional & Structural Requirements
* **Exact Array Locations**: Child and value arrays must be mapped using the pre-allocated capacity `max_size` (not the active `size`), ensuring fixed offsets inside the page.
* **Binary Routing Complexity**: Traversals must navigate paths in $O(\log N)$ scale checks.
* **Tombstone Safeties**: Leaf searches must reject lookups if target slots are invalid.
* **Boundary Checks**: Any index offset calculation that exceeds active metadata limits must return invalid search structures.
