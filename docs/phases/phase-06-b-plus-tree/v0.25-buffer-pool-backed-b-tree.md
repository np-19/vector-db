## 1. Problem Statement

## Visual Model

```mermaid

    A["Key lookup"] --> B["B+ tree traversal"] --> C["Leaf entry"] --> D["Record RID"]
```

Accessing disk storage directly during B+ Tree traversals is extremely slow. We must route all index node page lookups through the `BufferPoolManager` cache. In multi-threaded environments, we must also implement a traversal protocol called **Latch Crabbing** (pin coupling) that pins parent and child nodes in RAM, releasing parent nodes only after child nodes are pinned, ensuring search threads never read unpinned memory and avoiding cache-pin leaks.

## 2. Step-by-Step Instructions

### Step 1: Design the Buffer-Pool-Backed B+ Tree Class
* Create a header file `src/index/buffer_btree.h` within `namespace DB`.
* Include the helper and buffer pool manager headers.
* Define `class BufferBTree`:
  * Declare private member variables:
    * `bpm` (pointer to `BufferPoolManager`).
    * `root_page_id` (PageID/int64_t).
  * Write a constructor composition mapping `bpm` and `root_page_id`.
  * Declare a public point lookup query method:
    * `RID Find(int64_t key)`: Searches for key references routing searches through the buffer pool cache.

### Step 2: Implement Latch Crabbing Search
* Implement `Find(key)`:
  * If `root_page_id == INVALID_PAGE_ID`, return an invalid RID immediately.
  * Set `current_id = root_page_id`.
  * **Fetch Root**: Call `current_page = bpm->FetchPage(current_id)`. If the returned pointer is null, throw a `std::runtime_error` (cache allocation failure).
  * **Crabbing Traversal Loop**:
    * Access the B+ Tree header on `current_page`.
    * **If Leaf Node**:
      * Search the leaf keys array for `key` using binary search (`std::lower_bound`).
      * If found, extract the matching `RID` from values.
      * **Unlock Leaf**: Call `bpm->UnpinPage(current_id, false)` to decrement the pin count.
      * Return the search result.
    * **If Internal Node**:
      * Search the internal keys using binary search (`std::upper_bound`) to find the child pointer index.
      * Extract the target child ID: `next_id = children[child_index]`.
      * **Fetch Child**: Call `next_page = bpm->FetchPage(next_id)`.
      * **Leak Guard Check**: If `next_page` is null:
        * Call `bpm->UnpinPage(current_id, false)` to release the parent node before throwing an exception, preventing a pin count leak.
        * Throw a `std::runtime_error`.
      * **Crab Release**: Call `bpm->UnpinPage(current_id, false)` to unpin the parent node now that the child page is pinned.
      * Update pointers: `current_id = next_id`, `current_page = next_page`.
      * Repeat the crabbing loop.

## 3. C++ Systems Features Primer

* **Latch Crabbing (Coupling)**: A synchronization pattern used during tree traversal. Instead of locking the entire tree (which blocks all other threads), a search thread places its hands on a parent node, grabs the child node, and then releases the parent. This keeps the locked region minimal, enabling high database concurrency.
* **Pin Leak Prevention**: A common systems bug. Every call to `FetchPage` increments the page's pin count. If your search loop exits early (e.g. throws an exception) and misses the matching `UnpinPage` call, that page remains locked in RAM forever. You must write leak guards that release held parent pointers before throwing errors.
* **Cache Pins**: The crabbing protocol ensures that the active page pointer is locked in RAM during evaluation. The compiler is guaranteed that the memory buffer address returned by `FetchPage` will not change until `UnpinPage` is called.

---

## 4. Functional & Structural Requirements
* **Exact Pin Matching**: Every fetch call must be paired with an unpin call on all execution paths (including error states).
* **RAM Routing**: The search traversal must run entirely on memory frames managed by the buffer pool manager, avoiding direct disk file queries.
* **Pin Release Sequence**: The parent page must be unpinned only *after* the child page has been successfully fetched and pinned.
* **Reset Integrity**: The page table pin counts must return to their initial state after the index lookup concludes.
