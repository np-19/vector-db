## 1. Problem Statement

## Visual Model

Physical disk hardware is susceptible to data corruption caused by power cuts, hardware degradation (bit rot), or driver glitches. If the database loads a corrupted page, it will process garbage data, causing runtime crashes or corrupting other pages. We need to implement an automatic **Page Validation** engine using CRC32 checksums to verify page integrity on every read and write operation.

---

## 2. Step-by-Step Instructions

### Step 1: Implement the CRC32 Checksum Utility
* Create a header file `src/common/checksum.h` within `namespace DB`.
* Implement a CRC32 calculator function:
  * Input: A pointer to a byte array (`const uint8_t* data`) and the size of the array.
  * Output: A 32-bit unsigned integer (`uint32_t`) representing the checksum.
  * Algorithm: Use the standard IEEE CRC32 polynomial (`0xEDB88320`). Implement a table-driven CRC32 algorithm.
  * (Optional/Advanced) Write the CRC32 table generator as a `constexpr` function so the 256-entry lookup table is calculated at compile-time, ensuring zero startup execution overhead.

### Step 2: Inject Checksum Updates during Writes
* Open `src/storage/disk_manager.cpp`.
* Include the checksum header.
* Update `WritePage(PageID page_id, Page* page)`:
  * Before writing the page bytes to disk, calculate the CRC32 checksum of the page's data payload (`page->data` of size `PAGE_DATA_SIZE`).
  * Store this calculated checksum in the page header: `page->header.checksum = calculated_val;`.
  * Write the page structure to the disk file as normal.

### Step 3: Validate Page Checksums during Reads
* Update `ReadPage(PageID page_id, Page* page)`:
  * Read the page bytes from the disk file into the `page` structure as normal.
  * Skip validation if the loaded page's type is `PageType::FREE_PAGE` or if the page is completely blank.
  * Calculate the CRC32 checksum of the loaded page's data payload (`page->data` of size `PAGE_DATA_SIZE`).
  * Compare the calculated checksum with the checksum stored in the loaded page's header: `page->header.checksum`.
  * If they do not match, throw a `std::runtime_error` containing the Page ID (e.g. `"Database corruption detected: Checksum mismatch on Page 5"`).

## 3. C++ Systems Features Primer

* **Data Checksums**: A checksum is a mathematical signature generated from a stream of bytes. If even a single bit in the data array flips from `0` to `1` (corruption), calculating the checksum again will yield a completely different number, exposing the corruption.
* **CRC32 (Cyclic Redundancy Check)**: A widely used checksum algorithm that divides the input byte stream bit-by-bit using a binary polynomial. Implementing this bit-by-bit is slow, so systems databases pre-calculate a 256-entry lookup table containing results for every possible byte value, accelerating the scan.
* **Compile-Time Table Generation (`constexpr`)**: In modern C++, declaring functions as `constexpr` tells the compiler: *"Execute this calculation during compilation, and embed the final static table directly into the compiled program."* This eliminates table generation delays when the database boots.
* **Strict Memory Boundaries**: When calculating the checksum, pass only the pointer to `page->data` and size `PAGE_DATA_SIZE`. Never calculate the checksum on the entire `Page` struct because the header contains fields that change dynamically (like `pinCount`), which would invalidate the checksum.

---

## 4. Functional & Structural Requirements
* **Automatic Verification**: Checksum calculation and validation must execute transparently inside the `ReadPage` and `WritePage` pipeline.
* **Payload Isolation**: The checksum must validate only the `data` array segment of the page, avoiding variable header fields.
* **Corruption Halts**: Any checksum validation failure must throw a C++ `std::runtime_error`, halting execution on that page immediately.
* **Efficiency**: The checksum algorithm must run in linear time $O(N)$ where $N$ is the page data size, using pre-computed lookup tables.
