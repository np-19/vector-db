# v0.49 -- Versioned Record Headers

---

## 1. Problem Statement

## Visual Model

Standard database records are overwritten in place when updated, destroying their previous values. To support concurrent reads without locking (MVCC - Multi-Version Concurrency Control), we must store multiple versions of each record simultaneously, allowing each transaction to see the snapshot of data at the time it started. We need to design a per-record version header (**`MVCCRecordHeader`**) that stores the creator transaction ID (`xmin`), the deleter transaction ID (`xmax`), and a pointer to the previous version slot, enabling the visibility engine to evaluate which version to expose to each reader.

---

## 2. Step-by-Step Instructions

### Step 1: Design the MVCC Record Header Struct
* Create a header file `src/storage/mvcc_record.h` within `namespace DB`.
* Include the type and RID headers.
* Apply compiler struct byte-packing pragmas:
  * Add `#pragma pack(push, 1)` before the struct definition.
  * Add `#pragma pack(pop)` after.
* Define `struct MVCCRecordHeader`:
  * Declare struct fields:
    * `xmin` (type `TxID`): The transaction ID that **created** this version of the record. Set to `INVALID_TXN_ID` until a write starts.
    * `xmax` (type `TxID`): The transaction ID that **deleted or replaced** this version. Initialized to `INVALID_TXN_ID` (meaning the record has not been deleted yet).
    * `prev_version_rid` (type `RID`): A record pointer containing the Page ID and slot index of the previous version of this record on disk.
  * Write a default constructor initializing `xmin = INVALID_TXN_ID`, `xmax = INVALID_TXN_ID`, and `prev_version_rid = RID(INVALID_PAGE_ID, 0)`.
  * Write a parameterized constructor initializing all three fields.

## 3. C++ Systems Features Primer

* **Multi-Version Concurrency Control (MVCC)**: Instead of locking records for writes, MVCC creates new version snapshots on every update. When Transaction A reads a row, it sees the version committed before it started. When Transaction B modifies the same row, it creates a new version without touching A's view. The two transactions never block each other.
* **Struct Packing (`#pragma pack`)**: By default, the compiler adds invisible padding bytes between struct fields to align them to CPU word sizes. This saves instruction cycles but wastes disk space. For fixed-width disk page headers, we use `#pragma pack(push, 1)` to enforce 1-byte alignment, ensuring the struct occupies the exact minimum byte count needed.
* **xmin/xmax Semantics**: These two TxID stamps are the core visibility mechanism. An undeleted record has `xmax == INVALID_TXN_ID`. A deleted record has `xmax` set to the TxID of the transaction that deleted it.

---

## 4. Functional & Structural Requirements
* **Packed Layout**: The struct must be declared inside `#pragma pack(push, 1)` / `#pragma pack(pop)` boundaries.
* **Default-Safe Initialization**: Both `xmin` and `xmax` must default to `INVALID_TXN_ID`.
* **Chained Versions**: `prev_version_rid` must be capable of storing `INVALID_PAGE_ID` indicating the head of a version chain.
* **Binary Size Check**: The struct must occupy exactly `sizeof(TxID) + sizeof(TxID) + sizeof(RID)` bytes when packed.
