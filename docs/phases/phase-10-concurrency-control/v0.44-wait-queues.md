## 1. Problem Statement

## Visual Model

When multiple transactions queue up waiting for the same database resource, the concurrency engine must prevent **Starvation** (where an older transaction waits forever because newer incoming transactions keep jumping ahead in line). The manager must process requests in strict **FIFO (First-In, First-Out)** order. If a transaction is aborted (due to timeouts or deadlocks) while waiting in a queue, its request must be immediately pruned from the queue to prevent orphan requests from blocking the queue scheduler.

## 2. Step-by-Step Instructions

### Step 1: Design the Wait Queue Optimizer
* Create a header file `src/concurrency/wait_queue.h` within `namespace DB`.
* Include the lock manager headers.
* Define `class WaitQueueHelper`:
  * Declare a public static cleanup method:
    `static void CleanUpOnAbort(LockRequestQueue& queue, TxID txn_id)`

### Step 2: Implement Iterator-Safe Queue Pruning
* Implement `CleanUpOnAbort(queue, txn_id)`:
  * Declare `found = false`.
  * **Scan Queue**: Loop through the `queue.requests` list using list iterators:
    * Set `it = queue.requests.begin();`.
    * Loop while `it != queue.requests.end()`:
      * Check if `it->txn_id == txn_id`:
        * If yes, erase the request. Assign the returned iterator to preserve loop cursor safety:
          `it = queue.requests.erase(it);`
        * Set `found = true`.
      * If no, increment the iterator: `++it;`.
  * **Recalculate & Notify**: If `found` is `true`:
    * Reset the queue status: `is_shared_locked = false` and `is_exclusive_locked = false`.
    * Loop through the remaining requests in the queue list. For each request where `is_granted` is true, re-apply the locking flags:
      * Set `is_shared_locked = true` if SHARED.
      * Set `is_exclusive_locked = true` if EXCLUSIVE.
    * Wake up remaining waiting threads: Call `queue.cv.notify_all();`.

## 3. C++ Systems Features Primer

* **Starvation**: A concurrency anomaly where a thread is perpetually denied resource access because other threads are prioritized. We prevent this in the lock manager by:
  1. Appending incoming requests to the back of the queue list.
  2. Granting locks only when a request reaches the front of the queue, or if all preceding requests in the list are compatible.
* **List Erasure & Iterator Invalidation**: In C++, erasing elements from a container invalidates iterators pointing to those elements. In a loop, writing `list.erase(it)` and then calling `++it` will trigger memory faults and crash the program. The `erase()` method returns a new, valid iterator pointing to the element immediately following the deleted node. We write `it = list.erase(it)` to keep the loop cursor safe.
* **Orphan Request Cleanup**: If a transaction aborts but remains in the lock table wait list, the manager will treat it as active, blocking all subsequent requests. The rollback and abort pipelines must clean up these records immediately.

---

## 4. Functional & Structural Requirements
* **Total Pruning**: All matching transaction requests must be completely removed from the wait queue.
* **State Updates**: Removing an aborted request must trigger a recalculation of the queue's locking status flags.
* **Safety Iteration**: Pruning loops must assign the return value of `erase()` to prevent iterator invalidation crashes.
* **Wakeup Signals**: Waking up waiting threads via `cv.notify_all()` must execute if any request was pruned.
