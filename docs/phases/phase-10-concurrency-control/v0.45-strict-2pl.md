# v0.45 -- Strict 2-Phase Locking Protocol

## 1. Problem Statement

## Visual Model

Releasing write locks early allows concurrent transactions to read uncommitted modifications. If the first transaction subsequently aborts, the second transaction has read corrupt data (dirty reads), causing cascading rollbacks. To satisfy Serializability, the concurrency engine must enforce the **Strict 2-Phase Locking (Strict 2PL)** protocol: a transaction can acquire locks during its execution (Growing Phase), but it must hold all locks until the transaction commits or aborts, and then release them in a single operation (Shrinking Phase). We need to implement a Strict 2PL coordinator (**`Strict2PL`**) that manages this finalization release pipeline.

## 2. Step-by-Step Instructions

### Step 1: Design the Strict 2PL Coordinator
* Create a header file `src/concurrency/strict_2pl.h` within `namespace DB`.
* Include the transaction and lock manager headers.
* Define `class Strict2PL`:
  * Declare a public static release helper method:
    `static void ReleaseAllLocks(const std::shared_ptr<Transaction>& txn, LockManager* lock_manager)`

### Step 2: Implement Release Coordination
* Implement `ReleaseAllLocks(txn, lock_manager)`:
  * Retrieve the transaction's unique ID: `txn_id = txn->GetTxID();`.
  * Retrieve the list of locked resources: `locks = txn->GetHeldLocks();`.
  * **Release Iteration Loop**: Loop through all locked record coordinates (`RID`) in the vector:
    * Call the lock manager release interface:
      `lock_manager->Release(txn_id, rid);`
      *(This updates lock table flags and wakes up waiting transactions).*
  * **Clear Registry**: Call `txn->ClearLocks();` to reset the transaction's lock list.

## 3. C++ Systems Features Primer

* **Strict 2-Phase Locking (Strict 2PL)**: A protocol that guarantees serializable execution schedules. It divides lock management into two phases:
  1. **Growing Phase**: The transaction acquires locks. It is not allowed to release any locks.
  2. **Shrinking Phase**: Occurs at transaction commit or abort. All locks are released in a single operation.
  By holding all locks until finalization, we prevent other transactions from reading uncommitted data, satisfying isolation guarantees.
* **Cascading Rollback Prevention**: If transaction A changes a row and releases its lock early, transaction B can read the change. If transaction A aborts, it rolls back. This forces transaction B to abort as well because it read fake data. If transaction B passed data to transaction C, then C must abort. This chain reaction (cascading rollback) is expensive and is prevented by Strict 2PL.

---

## 4. Functional & Structural Requirements
* **Single-Phase Releases**: All locks held by the transaction must be released during transaction commit or abort finalization, never during execution.
* **Complete Cleanup**: Releasing locks must clear the transaction's internal lock list.
* **Notification Propagation**: Every release call must notify the lock manager to wake up waiting threads.
* **Const Protection**: Release operations must not mutate the target transaction's TxID.
