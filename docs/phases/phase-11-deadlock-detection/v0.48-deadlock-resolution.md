## 1. Problem Statement

## Visual Model

```mermaid

    A["Waiting transactions"] --> B["Wait-for graph"] --> C["Cycle detector"] --> D["Victim rollback"]
```

When a deadlock cycle is detected, the database engine cannot simply wait; it must take action to break the gridlock, or the conflicting threads will remain suspended forever. We need to implement a **Deadlock Resolver** optimizer class (**`DeadlockResolver`**) that builds the Wait-for Graph, runs cycle detection, selects the youngest transaction (the one with the highest TxID) in the loop as a victim, aborts the victim to minimize rollback costs, and releases its held locks to clear the gridlock.

## 2. Step-by-Step Instructions

### Step 1: Design the Deadlock Resolver
* Create a header file `src/concurrency/deadlock_resolver.h` within `namespace DB`.
* Include the transaction, lock manager, cycle detector, and Strict 2PL headers.
* Define `class DeadlockResolver`:
  * Declare a public static execution method:
    `static void ResolveDeadlock(TransactionManager* txn_manager, LockManager* lock_manager, const std::unordered_map<TxID, std::shared_ptr<Transaction>>& active_txns)`

### Step 2: Implement Victim Selection & Aborts
* Implement `ResolveDeadlock(txn_manager, lock_manager, active_txns)`:
  * **Build Graph**: Reconstruct the `WaitForGraph` by scanning all queues in the lock table, adding dependency edges pointing from waiting transactions to granted transactions.
  * **Detect Cycle**: Call `CycleDetector::DetectCycle()` to search for loops in the graph.
  * **Select Victim**: If a cycle is detected, identify the victim `victim_id`:
    * Scan the transaction nodes in the cycle.
    * Apply the **youngest-transaction heuristic**: Select the transaction with the highest `TxID` (this is the youngest transaction, which has performed the least amount of write work).
  * **Execute Abort**:
    * Locate the corresponding `Transaction` shared pointer in the `active_txns` registry map.
    * Call the transaction manager abort method:
      `txn_manager->Abort(victim_txn);`
    * Call the Strict 2PL release method to clear all locks held by the victim:
      `Strict2PL::ReleaseAllLocks(victim_txn, lock_manager);`
      *(This deletes the locks from the lock table queues and wakes up the remaining waiting transaction threads, breaking the deadlock).*

## 3. C++ Systems Features Primer

* **Deadlock Resolution Heuristics**: When a deadlock cycle forms, we must choose which transaction to abort. Two common heuristics are:
  * **Oldest-Transaction Heuristic**: Aborts the youngest transaction, keeping the oldest transaction running.
  * **Youngest-Transaction Heuristic**: Aborts the youngest transaction (highest TxID). Since the youngest transaction has been active for the shortest time, it holds fewer locks and has written fewer pages. Reverting its changes is fast and cheap.
* **Background Sweeper Threads**: In production database engines, deadlock detection does not block query execution. A separate daemon thread runs in the background. It sleeps for a configured duration (e.g. 500 milliseconds), wakes up, locks the lock table mutex, builds the graph, resolves cycles, and goes back to sleep.
* **Lock Cleanup Sequencing**: Changing a transaction's state to `ABORTED` is not enough. If we forget to call `ReleaseAllLocks()`, the locks remain in the lock table, keeping the other transaction blocked forever. We must trigger the release sequence to wake up waiting threads.

---

## 4. Functional & Structural Requirements
* **Heuristic Selection**: The resolver must select the youngest transaction (highest TxID) inside the deadlock loop as the victim.
* **Complete Release**: Aborting a victim must change its state to `ABORTED` and release all its locks in the lock table immediately, waking up survivors.
* **Non-Blocking Operation**: The resolver must run dynamically without halting execution of transactions that are not part of the deadlock cycle.
* **Const Correctness**: Graph evaluations must not mutate active transaction parameters.
