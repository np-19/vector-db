# v0.14 -- Page Pinning, Unpinning, & Cache Routing

---

## 1. Problem Statement

## Visual Model

```mermaid
flowchart LR
    A["Page request"] --> B["Buffer pool"] --> C["Pinned frame"] --> D["Disk manager"]
```
In a multi-threaded database, multiple queries read and write pages concurrently. If thread A is reading a page in memory, and thread B concurrently evicts that same page to load a different one, thread A will read corrupt memory, causing a crash. We must implement a **Pin/Unpin Protocol** that tracks page usage using active pin counts, locking pages in RAM while threads are reading them, and releasing them for eviction only when their pin counts drop to `0`.

## 2. Step-by-Step Instructions

### Step 1: Implement Page Fetching & Cache Matching
* Open `src/buffer/buffer_pool_manager.cpp`.
* Implement `Page* FetchPage(PageID page_id)`:
  * Acquire an exclusive write lock (`std::unique_lock<std::shared_mutex>`) on the `bpm_mutex`.
  * **Scenario A (Cache Hit)**: Check if `page_id` is present in the `page_table` map:
    * If found, increment the frame's `pin_count` in metadata.
    * Return the pointer to the memory frame inside the cache array: `&pages[frame_id]`.
  * **Scenario B (Cache Miss)**: If not found in the map:
    * **Locate Frame**: Check if `free_list` is not empty.
      * If not empty: Pop the first empty frame index from the list.
      * If empty: Call `SelectVictim(&frame_id)` to run the eviction algorithm.
        * If eviction fails (all pages are pinned), return `nullptr` (out of cache memory!).
        * If eviction succeeds, erase the evicted page's ID mapping from the `page_table`.
    * **Load Data**: Read the page from disk directly into the target frame buffer:
      `disk_manager->ReadPage(page_id, &pages[frame_id]);`
    * **Update Mappings**: Add the new mapping to the `page_table`: `page_table[page_id] = frame_id`.
    * **Set Metadata**: Initialize the frame metadata: `page_id = page_id`, `pin_count = 1`, `is_dirty = false`, `reference_bit = true`.
    * Return a pointer to `pages[frame_id]`.

### Step 2: Implement Page Unpinning
* Implement `bool UnpinPage(PageID page_id, bool is_dirty)`:
  * Acquire an exclusive lock on `bpm_mutex`.
  * Find `page_id` in the `page_table` map. If not found, return `false`.
  * Retrieve the frame index. Check if `pin_count == 0`. If yes (already unpinned), return `false`.
  * Decrement `pin_count`.
  * If the parameter `is_dirty` is `true`, update the frame metadata: `is_dirty = true`.
  * Return `true`.

### Step 3: Implement Page Allocation
* Implement `Page* NewPage(PageID* page_id)`:
  * Acquire an exclusive lock.
  * **Locate Frame**: Find a frame ID (pop from `free_list` or call `SelectVictim`). If all frames are pinned, return `nullptr`.
  * **Allocate ID**: Call `disk_manager->AllocatePage()` to allocate a new Page ID on disk, saving the ID to the output pointer.
  * **Initialize**: Clear the selected page buffer: `pages[frame_id].Reset()`. Set the page ID in the page's header.
  * **Initialize on Disk**: Write the blank page to disk immediately to format the file block.
  * **Update mappings**: Add the mapping to `page_table` and initialize frame metadata (`page_id = *page_id`, `pin_count = 1`, `is_dirty = false`, `reference_bit = true`).
  * Return a pointer to `pages[frame_id]`.

## 3. C++ Systems Features Primer

* **Thread Safety in Caches**: The lookup maps (`page_table`) and list queue structures (`free_list`) are accessed by multiple concurrent threads. If two threads modify these maps simultaneously without locking, the structures get corrupted (race conditions). We guard the fetch, unpin, and new page paths using `std::unique_lock` to block concurrent access during modifications.
* **Cache Hits vs. Cache Misses**:
  * **Hit**: Page exists in memory. Fetching takes under 1 microsecond.
  * **Miss**: Page exists only on disk. Fetching requires reading from disk, which takes ~5-10 milliseconds (thousands of times slower).
* **Pin Count Leaks**: A common bug in database engines. Every time you fetch a page, you increment its pin count. You must call `UnpinPage` when you finish reading/writing. If you forget to call `UnpinPage`, the frame remains pinned forever. If all frames become pinned, the buffer pool is locked and future page lookups will return null.

## 4. Functional & Structural Requirements
* **Cache Routing**: `FetchPage` must check the `page_table` first, preventing redundant disk reads.
* **Dirty Propagations**: If any thread unpins a page using `is_dirty = true`, the frame metadata's dirty flag must remain `true` until the page is written to disk.
* **Eviction Guard**: The eviction algorithm must bypass any frame slot where `pin_count > 0`.
* **Zero Initialized**: `NewPage` must write a zero-initialized block of size 4096 bytes to disk before returning.
