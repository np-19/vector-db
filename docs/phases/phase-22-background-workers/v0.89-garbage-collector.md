# v0.89 -- Garbage Collector Worker

## 1. Problem Statement

## Visual Model

```mermaid
flowchart LR
    A["Worker schedule"] --> B["Maintenance task"] --> C["Checkpoint or cleanup"] --> D["Healthy storage"]
```
Dead MVCC record versions accumulate on disk pages whenever transactions update or delete documents. Without periodic cleanup, disk usage grows unboundedly. We need a **`GarbageCollectorWorker`** that extends `BackgroundWorker` and periodically triggers the `GCCoordinator::RunGCSweep()`, reclaiming disk space from dead record versions safely using the oldest active transaction ID as the safety boundary.

## 2. Step-by-Step Instructions

### Step 1: Design the GC Worker
* Create a header file `src/workers/gc_worker.h` within `namespace DB`.
* Include the background worker and GC coordinator headers.
* Define `class GarbageCollectorWorker : public BackgroundWorker`:
  * Declare private member variables:
    * `gc_coordinator` (pointer to `GCCoordinator`).
  * Write a constructor accepting `GCCoordinator*` and a sleep interval in milliseconds.
  * Implement the protected override:
    `void RunTask() override`

### Step 2: Implement the GC Task
* Implement `RunTask()`:
  * Log: *"GCWorker: Starting MVCC garbage collection sweep..."*
  * Call `gc_coordinator->RunGCSweep()`.
  * Log: *"GCWorker: GC sweep complete."*

## 3. C++ Systems Features Primer

* **GC Frequency Trade-off**: Running GC too frequently wastes I/O reading every page to check for dead slots. Running too infrequently wastes disk. A reasonable interval is every 5–10 minutes, or triggered when dirty page fractions exceed a configurable threshold.
* **Write Amplification**: GC reads each page, erases dead slots, compacts, and writes the page back. This produces extra write I/O ("write amplification"). In SSD-based systems, this contributes to SSD wear, so GC frequency must be tuned carefully.
* **Background Safety**: GC runs on a background thread and must not hold locks that would block concurrent read transactions. The purging loop should acquire short-lived per-page locks, release them immediately after writing each page, and proceed to the next.

---

## 4. Functional & Structural Requirements
* **Periodic Execution**: `RunTask()` triggers on the configured interval.
* **Non-Blocking**: Per-page locks must be held for the minimum duration possible.
* **Correctness**: GC must compute the safe threshold from the live transaction registry on every sweep.
