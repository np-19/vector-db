# v0.59 -- WAL Writer

---

## 1. Problem Statement

## Visual Model

```mermaid
flowchart LR
    A["Data change"] --> B["Log record"] --> C["WAL flush"] --> D["Page flush"]
```
Individual log records need to be batched in a RAM buffer and periodically flushed to a physical disk file to avoid performance penalties from synchronously writing a disk seek for every single insert. We need to implement a **`WALWriter`** class that maintains an in-memory log buffer, provides an `AppendRecord()` method to serialize and push records into the buffer, and a `ForceFlush()` method that writes the entire buffer to the physical WAL file using OS-level flush operations.

---

## 2. Step-by-Step Instructions

### Step 1: Design the WAL Writer Class
* Create a header file `src/recovery/wal_writer.h` within `namespace DB`.
* Include the log record, file stream (`<fstream>`), mutex, and vector headers.
* Define `class WALWriter`:
  * Declare private member variables:
    * `wal_file` (type `std::ofstream`): Open file stream to the WAL log file.
    * `log_buffer` (type `std::vector<uint8_t>`): In-memory byte buffer accumulating serialized log records.
    * `last_appended_lsn` (type `LSN`): Tracks the highest LSN appended to the buffer.
    * `buffer_mutex` (type `std::mutex`): Thread-safety protection for the buffer.
  * Write a constructor accepting the WAL file path as `std::string`, opening the file in binary append mode: `wal_file.open(path, std::ios::binary | std::ios::app)`.
  * Declare public methods:
    * `void AppendRecord(const LogRecord& record)`: Serializes and buffers a log record.
    * `LSN ForceFlush()`: Writes and syncs the buffer to disk.

### Step 2: Implement Buffer Append
* Implement `AppendRecord(record)`:
  * Acquire an exclusive lock on `buffer_mutex`.
  * Create a `Serializer` and call `record.Serialize(serializer)`.
  * Copy the serialized bytes into `log_buffer` using `insert()` or `push_back()`.
  * Update `last_appended_lsn = record.lsn`.

### Step 3: Implement Force Flush
* Implement `ForceFlush()`:
  * Acquire an exclusive lock on `buffer_mutex`.
  * If `log_buffer` is empty, return `last_appended_lsn`.
  * Write the entire buffer to the WAL file:
    `wal_file.write(reinterpret_cast<const char*>(log_buffer.data()), log_buffer.size());`
  * Force the OS to flush its internal file cache:
    `wal_file.flush();`
  * Clear the in-memory buffer: `log_buffer.clear();`.
  * Return `last_appended_lsn`.

## 3. C++ Systems Features Primer

* **Double-Buffered I/O**: Writing to a disk on every log insert would be extremely slow. By batching records in a RAM buffer and writing them in bulk, we reduce the number of disk seeks dramatically.
* **OS Flush vs. Disk Sync**: Calling `flush()` on a C++ file stream forces the bytes to the OS kernel buffer. However, the kernel may still delay writing them to the physical disk platters. For true durability, you would additionally call the OS-level sync API (`fsync` on Linux, `_commit` on Windows). For this curriculum, `flush()` is sufficient.
* **Thread-Safe Buffer**: Multiple transaction threads call `AppendRecord()` concurrently. We protect the buffer with a mutex to prevent two threads from corrupting each other's byte writes.

---

## 4. Functional & Structural Requirements
* **Binary Append Mode**: The WAL file must be opened in binary append mode to prevent overwrites of historical records.
* **Thread Safety**: Both `AppendRecord()` and `ForceFlush()` must acquire the buffer mutex before touching the buffer.
* **Atomic Flush**: All bytes buffered since the last flush must be written in a single contiguous write call.
* **LSN Tracking**: `last_appended_lsn` must be updated on every append.
