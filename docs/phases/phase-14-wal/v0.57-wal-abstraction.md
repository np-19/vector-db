## 1. Problem Statement

To guarantee database durability during crashes, we need an append-only journal file called the **Write-Ahead Log (WAL)**. Before any page modification is written to the main database file, a description of that modification must first be recorded in the WAL and flushed to disk. We need to implement a **`WALManager`** class that manages a monotonically increasing **Log Sequence Number (LSN)** allocator, tracks the highest LSN flushed to physical disk, and wraps the WAL filepath configuration.

## 2. Step-by-Step Instructions

### Step 1: Design the WAL Manager Class
* Create a header file `src/recovery/wal_manager.h` within `namespace DB`.
* Create the directory `src/recovery/` if it does not exist.
* Include the type headers and the atomic, string, and utility headers.
* Define `class WALManager`:
  * Declare private member variables:
    * `next_lsn` (type `std::atomic<LSN>`): Monotonically increasing counter initialized to `1`.
    * `flushed_lsn` (type `std::atomic<LSN>`): Tracker for the highest LSN successfully written and synced to disk. Initialized to `0`.
    * `wal_filepath` (type `std::string`): Path to the WAL journal file.
  * Write a constructor: `explicit WALManager(std::string path)` storing the path.
  * Declare public methods:
    * `LSN AllocateLSN()`: Atomically increments and returns the next log sequence number.
    * `LSN GetFlushedLSN() const`: Returns the flushed LSN tracker value.
    * `void SetFlushedLSN(LSN lsn)`: Updates the flushed LSN tracker after a disk write.
    * `std::string GetWalFilepath() const`: Returns the WAL file path.

### Step 2: Implement Atomic Allocation
* Implement `AllocateLSN()`:
  * Return `next_lsn.fetch_add(1)`.
* Implement `GetFlushedLSN()`:
  * Return `flushed_lsn.load()`.
* Implement `SetFlushedLSN(lsn)`:
  * Call `flushed_lsn.store(lsn)`.

## 3. C++ Systems Features Primer

* **Write-Ahead Logging (WAL)**: The most fundamental crash-safety mechanism in databases. The WAL rule states: *"Never write a modified page to the main database file until the corresponding log record describing that modification has been flushed to the WAL file."* If power fails, we can reconstruct all committed changes by replaying the WAL log.
* **Log Sequence Numbers (LSNs)**: A unique, monotonically increasing 64-bit integer assigned to every log record. LSNs allow:
  1. **Ordering**: Replay operations in exact historical sequence.
  2. **Tracking**: Every page header stores the LSN of the last modification, allowing the recovery engine to skip replaying log records that are already reflected on the page.
* **Flushed LSN**: The boundary of durable changes. Any log record with `LSN <= flushed_lsn` is guaranteed to be on disk. Records with `LSN > flushed_lsn` are still in the in-memory WAL buffer.

---

## 4. Functional & Structural Requirements
* **Atomic Sequences**: `AllocateLSN()` must use `std::atomic<LSN>::fetch_add(1)` to prevent duplicate LSN assignments under concurrent thread writes.
* **Starting at 1**: The first allocated LSN must be `1`. LSN `0` is reserved for the "no WAL record" initialization state.
* **Flushed Barrier**: `GetFlushedLSN()` must reflect the actual highest LSN written and synced to disk.
