# v0.60 -- Commit Durability Flush Protocol

---

## 1. Problem Statement

## Visual Model

```mermaid
flowchart LR
    A["Data change"] --> B["Log record"] --> C["WAL flush"] --> D["Page flush"]
```
When a client sends a `COMMIT` request, the engine must guarantee the **Durability** property (the 'D' in ACID): committed data must survive power failures and system crashes. We need to implement a **`CommitDurability`** coordinator that enforces a strict commit sequence: allocate a commit log LSN, append a `COMMIT` record to the WAL, force-flush all log buffers to physical disk (blocking execution until confirmed), then and only then transition the transaction state to `COMMITTED` and return success to the caller.

---

## 2. Step-by-Step Instructions

### Step 1: Design the Commit Durability Coordinator
* Create a header file `src/concurrency/commit_durability.h` within `namespace DB`.
* Include the transaction, WAL writer, WAL manager, and log record headers.
* Define `class CommitDurability`:
  * Declare a public static commit execution method:
    `static void ForceCommitSync(const std::shared_ptr<Transaction>& txn, WALWriter* wal_writer, WALManager* wal_manager)`

### Step 2: Implement the Commit Sequence
* Implement `ForceCommitSync(txn, wal_writer, wal_manager)`:
  * **Step 1 — Allocate LSN**: Call `wal_manager->AllocateLSN()` to get a unique commit log sequence number.
  * **Step 2 — Create COMMIT Record**: Instantiate a `LogRecord` using the commit LSN, the transaction's TxID, and the `LogRecordType::COMMIT` type.
  * **Step 3 — Append to Buffer**: Call `wal_writer->AppendRecord(commit_record)`.
  * **Step 4 — Force Flush (Blocking)**: Call `LSN flushed = wal_writer->ForceFlush()`. This call **blocks execution** until all log bytes (including all previous insert/update records and this commit record) are written and synced to the WAL file on physical disk.
  * **Step 5 — Update Flushed LSN**: Call `wal_manager->SetFlushedLSN(flushed)`.
  * **Step 6 — Finalize State**: Set the transaction state to committed: `txn->SetState(TransactionState::COMMITTED)`.

## 3. C++ Systems Features Primer

* **Commit Ordering**: The most critical ordering invariant. Never call `txn->SetState(COMMITTED)` before `ForceFlush()` returns successfully. If you do, the client receives success confirmation before the data is on disk. A power failure a millisecond later would delete the data permanently, violating durability.
* **Group Commits**: The flush-per-commit approach is slow under high write loads. Production engines use "group commits": multiple transactions accumulate log records in the buffer simultaneously. A background flusher thread flushes all of them in a single disk write, amortizing the cost across many transactions.
* **I/O Cost of Durability**: Durable commits require disk syncs (expensive). Databases like PostgreSQL offer `synchronous_commit = off` to disable flush-per-commit, allowing the server to return success immediately at the cost of potentially losing the last few seconds of commits on crash.

---

## 4. Functional & Structural Requirements
* **Strict Step Ordering**: The state must change to `COMMITTED` only *after* `ForceFlush()` confirms the disk write.
* **Blocking Flush**: The commit call must block execution until the WAL file sync completes.
* **LSN Registry Update**: The WAL manager's `flushed_lsn` must be updated after every successful flush operation.
