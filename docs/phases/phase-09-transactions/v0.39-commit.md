## 1. Problem Statement

The **Durability** guarantee of transactions (the 'D' in ACID) states that once a transaction commits, its modifications must survive system crashes. To guarantee durability, a transaction commit must follow a strict, ordered execution sequence. We need to design and implement a commit coordination protocol (**`TxnCommitHelper`**) that logs the commit intention, flushes changes to physical disk storage, updates transaction states, and releases held locks in a sequence that prevents data anomalies.

## 2. Step-by-Step Instructions

### Step 1: Design the Commit Coordinator
* Create a header file `src/concurrency/txn_commit.h` within `namespace DB`.
* Include the transaction and memory headers.
* Define `class TxnCommitHelper`:
  * Declare a public static execution method:
    `static void ExecuteCommit(const std::shared_ptr<Transaction>& txn)`

### Step 2: Implement the Commit Sequence
* Implement `ExecuteCommit(txn)`:
  * **Step 1: Write Commit Log**: Append a `COMMIT` log record containing the transaction's `TxID` to the Write-Ahead Log (WAL) writer buffer (this is stubbed for now and integrated in Phase 14).
  * **Step 2: Flush Log**: Force-flush the WAL buffer to the physical disk file, calling the operating system's commit flush utility (`fsync` or `_commit`). We *must* block execution until the disk write operation completes.
  * **Step 3: Update State**: Call `txn->SetState(TransactionState::COMMITTED);` to finalize the state machine transition.
  * **Step 4: Release Locks**: Release all resource locks held in the transaction's registry map (such as slotted page Record ID locks), and notify the central lock manager (this is integrated in Phase 10).
  * Call `txn->ClearLocks();` to reset the transaction's logged locks vector.

## 3. C++ Systems Features Primer

* **The Commit Sequence Bug (Dirty Commits)**: A common bug in database engine design. If you release a transaction's locks *before* flushing its WAL log to disk, another concurrent transaction can immediately read the modified records and commit itself. If power cuts a millisecond later (before the first transaction's WAL log flushes), the first transaction's changes are lost (rolled back on boot). However, the second transaction is still committed, creating a corrupt database state (dirty read dependency).
* **Durability (ACID)**: Reached only when the transaction's logs are physically committed to disk. Database updates are fast because they write to memory cache blocks (RAM). The commit step is the checkpoint where RAM buffers are synced to disk, guaranteeing permanence.
* **Synchronous Blocks**: The commit helper blocks the calling thread until the disk manager reports that write operations have finished, guaranteeing durability before returning success.

---

## 4. Functional & Structural Requirements
* **Sequence Ordering**: Lock release operations must occur only *after* the transaction state changes to `COMMITTED`.
* **State Finalization**: The transaction's final state must be registered as `COMMITTED`.
* **Lock Cleanup**: All logged locks inside the transaction descriptor must be cleared.
* **Flush Blocking**: Commit logic must block execution until the WAL writer confirms page serialization.
