## 1. Problem Statement

When a document is deleted from the database, its corresponding HNSW node must be removed from the graph. Physically removing a node and re-wiring all its neighbors is complex and slow. Production HNSW implementations use **soft delete (tombstoning)**: the node is flagged as deleted and excluded from search results, while its graph links remain intact so that searches can still route through it to reach other nodes. We need to implement the `Delete()` method in `HNSWGraph` that sets the `is_deleted` tombstone flag and optionally compacts the node registry.

---

## 2. Step-by-Step Instructions

### Step 1: Implement the Soft Delete Method
* In `HNSWGraph`, declare a public method:
  `bool Delete(uint64_t node_id)`
* Implement `Delete(node_id)`:
  * Acquire the `graph_mutex`.
  * Check if `node_id` exists in `nodes`. If not, return `false`.
  * Set `nodes[node_id].is_deleted = true`.
  * Return `true`.

### Step 2: Handle Entry Point Deletion
* After marking the node deleted, check: `if (node_id == entry_node_id)`:
  * Scan `nodes` to find any non-deleted node with the highest layer level.
  * Set the found node as the new entry point.
  * If no non-deleted node exists: Set `entry_node_id` to an invalid sentinel value and `max_layer = 0`.

### Step 3: Understand Compaction (Concept)
* Soft deletes accumulate over time. If a large fraction of nodes are tombstoned, searches waste time routing through deleted nodes.
* Document: Periodically, a background GC can run a **graph rebuild**: iterate all non-deleted nodes and re-run the full `Insert()` pipeline on a fresh `HNSWGraph` object, discarding all deleted node data.

## 3. C++ Systems Features Primer

* **Soft vs. Hard Delete**: Hard-deleting a graph node requires reconnecting all its neighbors to each other (re-wiring the graph), which is computationally expensive. Soft delete is $O(1)$ but wastes graph traversal time on dead nodes. Real systems (like Qdrant, Weaviate) use a hybrid: soft delete for interactive deletes, periodic hard-rebuild for cleanup.
* **Entry Point Vulnerability**: If the global entry point node is deleted, no search can start. We must migrate the entry point to a different non-deleted node whenever the current entry is deleted.
* **Search Filter vs. Graph Skip**: Deleted nodes are filtered in **search result building** (excluded from returned results) but are **NOT** skipped during **graph traversal routing** (their links are still used to navigate to nearby non-deleted nodes).

---

## 4. Functional & Structural Requirements
* **Tombstone Marking**: `Delete()` must set `is_deleted = true` without removing the node from `nodes`.
* **Entry Point Safety**: If the deleted node is the entry point, a valid replacement entry must be selected.
* **Search Filter**: `Search()` must exclude deleted nodes from the returned `SearchResult` vector.
* **Thread Safety**: `Delete()` must acquire `graph_mutex` before modifying graph state.
