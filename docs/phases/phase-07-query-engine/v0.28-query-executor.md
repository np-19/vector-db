# v0.28 -- Query Executor & Volcano Iterator Interface

## 1. Problem Statement

## Visual Model

Materializing (loading) entire collections into memory to execute filter and projection operations consumes massive amounts of RAM and degrades latency. We need to design a query execution interface based on the **Volcano Iterator Model**. The interface must define query execution blocks (such as scans, filters, and limits) that stream records one-by-one on demand, bounding database memory usage to a constant size regardless of the dataset size.

---

## 2. Step-by-Step Instructions

### Step 1: Design the Abstract Executor Interface
* Create a header file `src/query/abstract_executor.h` within `namespace DB`.
* Include the document and RID headers.
* Define `class AbstractExecutor`:
  * Declare a public virtual destructor: `virtual ~AbstractExecutor() = default;`.
  * Declare pure virtual interface methods:
    * `virtual void Init() = 0`: Resets cursors, initializes variables, and prepares child executors.
    * `virtual bool Next(Document* doc, RID* rid) = 0`:
      * Pulls the next record in the stream.
      * Writes the document data directly to the memory address of the out-parameter pointer `doc`.
      * Writes the record ID directly to the memory address of the out-parameter pointer `rid`.
      * Returns `true` if a record was successfully retrieved; returns `false` if the query results are exhausted.

## 3. C++ Systems Features Primer

* **Volcano Iterator Model**: A database execution framework. Query operators are organized in a tree (e.g. a `LimitExecutor` sits on top of a `FilterExecutor`, which sits on top of a `SeqScanExecutor`).
  * The client triggers execution by calling `Next()` on the root node.
  * Each node calls `Next()` on its child node to pull a single record, processes it, and returns it up the tree.
* **Out-Parameters**: In performance-critical code, returning structures (like `Document`) by value from functions is slow because it creates copies of maps and arrays on the stack or heap. To optimize this, the caller allocates a single `Document` variable once, and passes its address as a pointer (`Document* doc`). The function writes data directly into the caller's memory block, bypassing allocations.
* **Bounded Memory Bounds**: By processing rows one-by-one, the database engine only needs to hold a single row's worth of data in RAM at a time. The database can scan a 100GB collection using only a few kilobytes of cache buffer memory.

---

## 4. Functional & Structural Requirements
* **Abstract Enforcement**: `AbstractExecutor` must be an abstract class, requiring child implementations to override `Init()` and `Next()`.
* **Out-Parameter Safety**: `Next` must write data to the memory addresses of the parameters provided by the caller, avoiding local copies.
* **Termination Signal**: Returning `false` from `Next()` must indicate the end of the query results stream.
* **Polymorphic Destructors**: The base class must declare a virtual destructor to prevent memory leaks during inheritance deallocations.
