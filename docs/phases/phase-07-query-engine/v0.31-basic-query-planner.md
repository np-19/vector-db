## 1. Problem Statement

## Visual Model

```mermaid

    A["Query text"] --> B["Parser"] --> C["Logical query"] --> D["Executor results"]
```

Database clients submit declarative filter constraints (e.g. `"age > 21"`) expressing *what* data they want to fetch, rather than procedural instructions describing *how* to find it. We need to implement a basic compilation engine class (**`QueryPlanner`**) that parses AST filter expressions, checks catalog registries to verify table and index availability, selects execution paths, and compiles the query into an executable tree of Volcano executors.

## 2. Step-by-Step Instructions

### Step 1: Design the Query Planner Class
* Create a header file `src/query/query_planner.h` within `namespace DB`.
* Include the abstract executor, seq scan, index scan, and catalog headers.
* Define `class QueryPlanner`:
  * Declare private member variables:
    * `record_manager` (pointer to `RecordManager`).
    * `catalog` (pointer to `Catalog`).
  * Write a constructor composition binding the dependencies.
  * Declare the compiler execution method:
    `std::unique_ptr<AbstractExecutor> PlanQuery(const std::string& collection_name, const Expr& filter)`

### Step 2: Implement Plan Compilation
* Implement `PlanQuery(collection_name, filter)`:
  * **Verify Namespace**: Check if `collection_name` exists in `catalog`. If not, throw a `std::runtime_error` (table not found).
  * **Inspect Filter**: Use C++ dynamic casting to inspect if the `filter` is comparison-based:
    `const BinaryExpr* bin_expr = dynamic_cast<const BinaryExpr*>(&filter);`
  * **Scenario A (Index Scan Path)**: If the cast succeeds:
    * (In a full engine, we traverse the AST to extract field names. For this basic version, we assume the target attribute is `"age"`).
    * Check if the catalog contains an index on this field: `catalog->HasIndex(collection_name, "age")`.
    * If yes:
      * Retrieve `IndexMetadata` from the catalog.
      * Instantiate and return an index scan planner:
        `return std::make_unique<IndexScanExecutor>(record_manager, idx_meta.root_page_id, start_range, end_range);`
  * **Scenario B (Sequential Scan Fallback)**: If the cast fails or no index exists:
    * Instantiate and return a sequential scanner:
      `return std::make_unique<SeqScanExecutor>(record_manager, catalog, collection_name);`

## 3. C++ Systems Features Primer

* **Declarative Query Processing**: Relational database systems separate logic from execution. Users write queries in SQL text or JSON maps describing *what* records they want. The query planner analyzes schemas and decides *how* to locate them, rewriting queries into physical machine executors.
* **Polymorphic Pointer Casting (`dynamic_cast`)**: In C++, base class pointers (like `const Expr&`) do not expose child variables. To inspect if an expression is a `BinaryExpr` so we can read its operator and fields, we cast the pointer at runtime using `dynamic_cast`:
  `const BinaryExpr* bin_expr = dynamic_cast<const BinaryExpr*>(&filter);`
  If the object is indeed a binary expression, the cast succeeds and returns its address; if not, it returns `nullptr`, allowing safe branching checks.
* **RTTI (Runtime Type Information)**: `dynamic_cast` relies on compiler RTTI tables. C++ only generates RTTI metadata for classes containing at least one virtual function. If the base class `Expr` is missing a virtual function (like `virtual ~Expr() = default;`), calling `dynamic_cast` will trigger compile-time errors.

## 4. Functional & Structural Requirements
* **Polymorphic Output**: The planner must return an instances of `std::unique_ptr<AbstractExecutor>`.
* **Collection Verification**: Planning queries on collections that do not exist in the catalog must throw a `std::runtime_error`.
* **Index Priority**: The planner must prioritize B+ Tree index scans over sequential table scans whenever a matching index is registered.
* **No-Throw Casts**: AST inspections must use `dynamic_cast` pointers, preventing compiler casting exceptions.
