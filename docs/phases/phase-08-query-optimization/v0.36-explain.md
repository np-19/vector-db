## 1. Problem Statement

## Visual Model


Queries that execute slowly are difficult to debug if you cannot see what decisions the optimizer made. Database administrators and engineers require a tool to inspect the selected execution path, index selections, and cost estimations. We need to implement an observability interface utility class (**`PlanExplainer`**) that formats physical query plans and their cost calculations into indented, human-readable ASCII layout tree strings.

## 2. Step-by-Step Instructions

### Step 1: Design the Plan Explainer Utility
* Create a header file `src/query/plan_explainer.h` within `namespace DB`.
* Include the physical plan and cost model headers, along with the `<sstream>` header.
* Define `class PlanExplainer`:
  * Declare a public static formatting helper:
    `static std::string Explain(const PhysicalPlanNode& plan, uint32_t num_pages, uint32_t num_rows, double selectivity)`

### Step 2: Implement Plan Formatting
* Implement `Explain(plan, num_pages, num_rows, selectivity)`:
  * Instantiate a stringstream: `std::stringstream ss;`.
  * **Calculate Costs**: Call `CostModel::EstimateCost()` passing the parameters to retrieve the `PlanCost` statistics.
  * Write the header prefix to the stream: `"Execution Plan:\n"`.
  * **Evaluate Operator**:
    * Check `plan.GetType()`:
      * **Case 1 (PhysicalSeqScan)**:
        * Cast the plan to `const PhysicalSeqScan*`.
        * Append details to the stream:
          * Operator name: `"PhysicalSeqScan"`.
          * Collection parameters: `"collection=[name]"`.
          * Cost metrics: `"[Estimated Cost: [total] (IO: [io], CPU: [cpu])]"`.
      * **Case 2 (PhysicalIndexScan)**:
        * Cast the plan to `const PhysicalIndexScan*`.
        * Append details to the stream:
          * Operator name: `"PhysicalIndexScan"`.
          * Parameters: `"collection=[col], field=[field], rootPageId=[page_id]"`.
          * Cost metrics: `"[Estimated Cost: [total] (IO: [io], CPU: [cpu])]"`.
  * Return the compiled buffer string: `return ss.str();`.

## 3. C++ Systems Features Primer

* **Query Observability**: In SQL databases, users prefix their queries with `EXPLAIN` (e.g. `EXPLAIN SELECT * FROM users WHERE age = 25;`). The database compiles and optimizes the query, but instead of running it, it returns a text diagram showing which indexes were chosen and the estimated cost metrics.
* **String Buffering (`std::stringstream`)**: In systems programming, concatenating strings using operators (like `str += "suffix"`) repeatedly is slow because it allocates new buffers and copies characters in memory on every addition. `std::stringstream` maintains a dynamic internal buffer, allowing fast additions using stream inserter operators (`<<`), converting types to text on the fly.
* **Tree Formatting (Indentation)**: To represent hierarchical operators (like a filter running on top of a sequential scan), the explainer prints prefix spaces proportional to the depth of the node (e.g. `std::string(depth * 2, ' ')`), making nested child operators easily readable.

## 4. Functional & Structural Requirements
* **API Return**: The explainer must return a formatted `std::string`.
* **Cost Verification**: The explained string must contain the exact computed cost numbers and parameters.
* **No Side Effects**: Calling `Explain()` must not mutate the physical plan or trigger database record modifications.
* **String Allocation Safety**: The text assembly pipeline must utilize stream-based buffering, preventing redundant string heap copies.
