# v0.82 -- MVCC-Aware Vector Search

---

## 1. Problem Statement

## Visual Model

```mermaid
flowchart LR
    A["Transaction"] --> B["Vector write or search"] --> C["MVCC visibility"] --> D["Transactional result"]
```
When executing a vector search inside a transaction, the HNSW graph may contain nodes from other uncommitted transactions that should be invisible to the current reader (MVCC snapshot isolation). We need to implement an **MVCC-aware search filter layer** that wraps the HNSW search results, loads each candidate document's MVCC header from disk, applies the visibility rules from the current snapshot, and discards invisible candidates before returning results to the caller.

---

## 2. Step-by-Step Instructions

### Step 1: Design the MVCC Vector Search Executor
* Create a header file `src/vector/mvcc_vector_search.h` within `namespace DB`.
* Include the HNSW graph, record manager, visibility, snapshot, and search result headers.
* Define `class MVCCVectorSearch`:
  * Declare private member variables: pointers to `HNSWGraph`, `RecordManager`.
  * Write a constructor.
  * Declare a public search method:
    `std::vector<SearchResult> Search(const Vector& query, int k, int ef, const Snapshot& snapshot, TxID active_txn_id)`

### Step 2: Implement MVCC-Filtered Search
* Implement `Search(query, k, ef, snapshot, active_txn_id)`:
  * Call `hnsw_graph->Search(query, k * 10, ef)` with over-fetch.
  * Declare `std::vector<SearchResult> visible_results`.
  * For each raw HNSW result:
    * Load the document page and slot from `result.rid` via the record manager.
    * Cast the slot payload to `MVCCRecordHeader*`.
    * Call `Visibility::IsVisible(*header, snapshot, active_txn_id)`.
    * If visible: Append `result` to `visible_results`.
  * Sort `visible_results` by ascending distance.
  * Truncate to `k`.
  * Return.

## 3. C++ Systems Features Primer

* **MVCC + Approximate Search**: HNSW returns approximate nearest neighbors. After applying MVCC visibility, some candidates may be filtered, leaving fewer than `k` results. By over-fetching (`k * 10`), we increase the probability of having at least `k` visible results after filtering.
* **Visibility Recall Trade-off**: If a large fraction of candidates are uncommitted (invisible), even over-fetching may yield fewer than k results. In this scenario, fallback to a brute-force scan of all visible records is the safe option.

---

## 4. Functional & Structural Requirements
* **Visibility Check on Every Result**: Every HNSW candidate must be checked against the MVCC visibility rules before inclusion in the final result.
* **Over-Fetch Buffer**: Must request `k * 10` candidates from HNSW to compensate for filtered-out invisible records.
* **Snapshot Immutability**: The snapshot passed to `Search()` must not be modified during the operation.
